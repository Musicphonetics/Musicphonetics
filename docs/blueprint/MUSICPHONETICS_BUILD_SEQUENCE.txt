======================================================================

======================================================================
3. NON-NEGOTIABLE WORK RULES
======================================================================

A. One phase at a time
- Work only on the current approved phase and its defined tasks.
- You may consider later phases when making architecture decisions, but do
  not implement them early without approval.
- Do not jump to a later part because it is visually exciting or easier.
- If a prerequisite is incomplete, stop and report it.

B. Complete workflows, not just screens
A feature is not done because its page looks finished. Verify the complete
journey, including data persistence, permissions, error states and tests.

C. Preserve data and functionality
- Never reset, overwrite, or fabricate production data to simplify a demo.
- Never casually drop tables, columns, policies, routes or integrations.
- Use focused, reversible changes and migrations.
- Before risky or irreversible changes, explain the risk and request approval.

D. Truthful status
Label features as:
- COMPLETE — acceptance criteria passed and evidence recorded.
- IN PROGRESS — implementation is underway.
- BLOCKED — a dependency or issue prevents safe progress.
- PLANNED — not implemented.
- NEEDS VERIFICATION — code exists but has not been adequately tested.
Never claim a feature, integration, payment, partnership or test works unless
that has actually been verified.

E. Security
- Authentication is not the same as authorisation.
- Enforce access on the server and database, including Supabase Row Level
  Security where applicable.
- Do not rely only on hiding buttons or frontend routes.
- Do not expose private student records, parent-child data, recordings,
  secrets, payment data or admin functions.
- Do not enable public admin registration.
- Treat minors' safety and recording privacy as important requirements.

F. Testing
Before marking a task complete:
- Run the relevant tests.
- Test the real user journey.
- Test invalid input and failure/empty states.
- Test access permissions where relevant.
- Check for regressions.
- Review the actual code diff.
- State which tests were not possible to run.

G. Design
- Follow the Musicphonetics brand and the Master Blueprint.
- Build a real app with independent routes, persistent navigation and
  role-specific workspaces.
- Do not revert to a universal sidebar containing every module.
- Do not put the whole authenticated application on one scrollable page.
- Do not create fake charts, fake activity, or decorative non-functional
  controls to make the product look complete.
- Make the experience responsive for mobile and desktop.

H. Scope discipline
Prefer one tested end-to-end workflow over many incomplete modules.
Do not add unrequested dependencies or unnecessary architecture.
Document material decisions and unresolved questions.

======================================================================
5. REQUIRED SESSION PROTOCOL
======================================================================

At the start of every coding session:

1. Read this build-sequence file.
2. Read the Master Blueprint or the relevant parts of it.
3. Read the current implementation status and relevant decision records.
4. Inspect the actual code related to the active task.
5. State the active phase and task.
6. State what is already working and what remains.
7. State the intended outcome, files/areas likely to change, dependencies,
   acceptance criteria and risks.
8. Do not repeat an already completed audit unless new evidence requires it.

During the session:
- Work on the active task only.
- Make small, reviewable changes.
- Preserve unrelated changes.
- Run relevant tests as you go.
- If blocked, stop and report the blocker instead of disguising it.

At the end of every session, report:
- Task and phase.
- Changes made.
- User-visible behaviour now working.
- Files/routes/services affected.
- Database migrations or policy changes.
- Tests actually run and results.
- Security/data considerations.
- Known limitations and outstanding issues.
- Whether acceptance criteria passed.
- Exact next task in the sequence.

Update IMPLEMENTATION_STATUS.md and relevant records before finishing.

6. MASTER IMPLEMENTATION ORDER
======================================================================

The numbers below refer to sections in MUSICPHONETICS_MASTER_BLUEPRINT.txt.
The order is intentional and is not the same as the numerical order in that
file. Some parts describe the final product, while other parts describe how
to build it.

PHASE 0 — DISCOVERY, AUDIT AND BASELINE
Blueprint references: Part 17, Part 18 (read only), Part 19, Part 16.

Task 0.1 — Audit the existing repository.
- Inspect the framework, routes, components, styling and deployment.
- Inspect authentication and session handling.
- Inspect Supabase schema, migrations and Row Level Security.
- Inventory existing student, parent, teacher, lesson, assignment and
  progress functionality.
- Inspect integrations and tests.
- Run the existing app and tests if safe.
- Identify broken routes, placeholders, duplicate logic and data risks.
- Do not undertake a major redesign or destructive migration.

Task 0.2 — Produce or update the audit records.
- Current functionality inventory.
- Route inventory.
- Data and permissions audit.
- Known defects and risks.
- Baseline test results.
- Reusable existing components and workflows.

Task 0.3 — Map the target architecture.
Read Part 2, Part 3, Part 13 and the relevant role sections of the Master
Blueprint. Map target routes and modules to the existing codebase. Record
which proposed screens already exist and which are new.

EXIT GATE 0:
The owner can review the actual baseline, key risks, proposed first change
and acceptance tests. No major implementation should begin until the audit
and first-phase plan have been presented.

PHASE 1 — APPLICATION SHELL AND REAL NAVIGATION
Blueprint references: Part 2, Part 3, Part 18.

Task 1.1 — Establish separate public and authenticated layouts.
Task 1.2 — Establish genuine independent routes.
Task 1.3 — Add or stabilise protected-route behaviour.
Task 1.4 — Implement role-appropriate navigation structures.
Task 1.5 — Implement loading, empty, error and not-found states.
Task 1.6 — Test direct route navigation, refresh, browser back/forward,
           sign-in, sign-out and session persistence.
Task 1.7 — Verify responsive mobile and desktop layouts.

Do not implement all the future modules. Use only the minimum set of route
destinations needed to prove the app shell works. Unbuilt destinations must
be clearly labelled or omitted, not presented as operational features.

EXIT GATE 1:
The app is no longer one long scrollable page. Routes and navigation work,
the authenticated shell is separate from the public website, and existing
working functionality remains accessible.

PHASE 2 — ACCOUNT IDENTITY, ONBOARDING AND PERMISSIONS
Blueprint references: Part 4, Part 13, Part 16.

Task 2.1 — Stabilise the existing registration and login flow.
Task 2.2 — Implement one primary identity selection: student, parent/guardian,
           teacher or musician.
Task 2.3 — Keep owner/admin out of public registration.
Task 2.4 — Implement role-specific onboarding and post-onboarding routing.
Task 2.5 — Preserve existing user records and handle existing users safely.
Task 2.6 — Enforce role and record permissions on the server/database.
Task 2.7 — Test cross-role and cross-user access attempts.

Do not create a casual universal role switcher. Any future additional role
must use a deliberate, authorised process.

EXIT GATE 2:
New and existing users reach the correct workspace. Role boundaries are
enforced beyond the frontend. Existing records are not lost or misassigned.

PHASE 3 — FIRST COMPLETE EDUCATION WORKFLOW
Blueprint references: Part 5, Part 6, Part 7, Part 13, Part 19.

This phase is the first major end-to-end vertical slice. Reuse the existing
portal wherever possible.

Task 3.1 — Teacher opens their authorised student list.
Task 3.2 — Teacher opens a student record.
Task 3.3 — Teacher records lesson details and attendance.
Task 3.4 — Teacher submits a lesson report with appropriate validation.
Task 3.5 — Teacher creates and publishes a practice assignment.
Task 3.6 — Student sees the assigned practice.
Task 3.7 — Student records completion or submits work, according to the
           supported implementation.
Task 3.8 — Teacher reviews the submission and provides feedback.
Task 3.9 — Parent sees the appropriate authorised learning update.
Task 3.10 — Verify record history, notifications where implemented,
            access controls, errors and regression behaviour.

Do not start marketplace, community or AI work before this core workflow
passes its acceptance tests unless the owner approves a documented exception.

EXIT GATE 3:
A real lesson-to-practice-to-feedback journey works with persisted data and
correct permissions. This is not satisfied by static mockups.

PHASE 4 — COMPLETE THE CORE STUDENT AND PARENT EXPERIENCES
Blueprint references: Part 5 and Part 6.

Task 4.1 — Student home, learning, lessons, practice and progress.
Task 4.2 — Recording/feedback history only to the extent supported.
Task 4.3 — Parent family overview and authorised child selection.
Task 4.4 — Child-specific lesson history and teacher updates.
Task 4.5 — Multi-child isolation and permission tests.
Task 4.6 — Empty states and useful first-run experience.

EXIT GATE 4:
Students and parents can reliably use the core learning records without
crossing account boundaries or seeing invented information.

PHASE 5 — TEACHER PROFESSIONAL WORKSPACE
Blueprint references: Part 7 and relevant shared-service sections.

Task 5.1 — Teacher home and action list.
Task 5.2 — Student management and search.
Task 5.3 — Lesson/calendar workflows supported by the current architecture.
Task 5.4 — Lesson reports and practice management.
Task 5.5 — Public profile editor and preview.
Task 5.6 — Enquiry management.
Task 5.7 — Subscription plan interface, initially without claiming live billing.
Task 5.8 — Permission and regression tests.

EXIT GATE 5:
The teacher workspace provides a coherent, working professional workflow.
Do not mark calendar, payments or subscriptions complete if only their
visual interface exists.

PHASE 6 — PUBLIC DISCOVERY AND ENQUIRIES
Blueprint references: Part 4 and Part 9.

Task 6.1 — Public teacher discovery and search.
Task 6.2 — Search filters based only on supported data.
Task 6.3 — Teacher profile details.
Task 6.4 — Enquiry submission and validation.
Task 6.5 — Enquiry storage, status and recipient access.
Task 6.6 — Notifications where implemented.
Task 6.7 — Test the visitor-to-enquiry journey.

EXIT GATE 6:
A visitor can discover a teacher and submit an enquiry that reaches the

PHASE 7 — MUSICIAN MARKETPLACE AND BOOKING PROTOTYPE
Blueprint references: Part 8, Part 9 and relevant parts of Part 13.

Task 7.1 — Musician profile and portfolio.
Task 7.2 — Discovery and supported filters.
Task 7.3 — Enquiry creation and management.
Task 7.4 — Availability and booking request model.
Task 7.5 — Explicit booking status lifecycle.
Task 7.6 — Notifications and communication where supported.
Task 7.7 — Test status transitions, duplicate requests and permissions.

EXIT GATE 7:
Musicians can manage enquiries and the booking prototype has clear,
testable statuses. Do not represent an enquiry as a confirmed booking.

PHASE 8 — SUBSCRIPTIONS AND PAYMENT TEST MODE
Blueprint references: Part 7, Part 8, Part 12 and Part 13.

Task 8.1 — Define plan entitlements before enforcing them.
Task 8.2 — Implement plan display for teacher and musician plans.
Task 8.3 — Implement the parent/family plan according to the blueprint.
Task 8.4 — Integrate supported payment-provider test mode if credentials and

Task 8.5 — Implement provider-side payment verification/webhooks correctly.
Task 8.6 — Handle pending, failed, cancelled and successful test transactions.
Task 8.7 — Test subscription status and entitlements.
Task 8.8 — Document production billing requirements separately.

EXIT GATE 8:
The demo clearly identifies test mode; payment state is not trusted from the
browser alone. Production billing remains disabled until separately approved

PHASE 9 — OWNER/ADMIN OPERATIONS
Blueprint references: Part 12 and Part 13.

Task 9.1 — Define admin permissions and audit requirements.
Task 9.2 — User and professional verification workflows.
Task 9.3 — Booking/enquiry oversight.
Task 9.4 — Support and moderation queues as their dependencies become ready.
Task 9.5 — Financial reporting with distinct revenue categories.
Task 9.6 — Test admin access and sensitive actions.

EXIT GATE 9:
Admin functions are private, authorised and auditable. Do not build admin

PHASE 10 — COMMUNITY AND EVENTS
Blueprint references: Part 10 and Part 13.

Task 10.1 — Define community data and access rules.
Task 10.2 — Build events and event details.
Task 10.3 — Build registration and status handling.
Task 10.4 — Implement reporting, moderation and content controls.

PHASE 11 — AI MUSIC-LEARNING PROTOTYPE

Task 12.4 — Error logging and monitoring review.

Task 12.6 — Accessibility and usability checks.

8. OWNER CHECKPOINTS AND APPROVAL GATES
======================================================================

The owner wants to check that work follows the agreed sequence. Therefore:

- At the start of each new phase, present a short plan and acceptance criteria.
- At the end of each phase, provide evidence of completion.
- Do not silently start the next phase if the current phase has failed its
  acceptance criteria.
- If the owner explicitly approves a phase transition, proceed.
- For low-risk tasks within an approved phase, make reasonable decisions
  without asking about every small detail.
- Always request approval before destructive data changes, production billing
  activation, significant permission changes, production infrastructure
  changes or material deviations from the product blueprint.

Evidence may include:
- Routes and files changed.
- Test output.
- Screenshots or a short walkthrough where available.
- Reproducible steps to verify a workflow.
- Database migration/policy details.
- Known limitations.

Do not claim to have visually inspected a screen if no visual inspection was
performed.

10. WHAT TO DO WHEN A SESSION ENDS MID-TASK

- Do not mark it complete.

- Resume from the last verified state next time.

Never repeat the whole project audit every day. Reinspect the relevant files
and status, then continue from the last verified checkpoint.
